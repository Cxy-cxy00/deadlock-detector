1 ปัญหาที่เครื่องมือนี้แก้

deadlock เป็นบั๊กที่ไม่ยอมบอกอะไรเลย

โปรแกรมหลาย thread ที่ล็อก mutex สลับลำดับกันจะค้างทั้งโปรแกรม อาการที่เห็นคือ เงียบไปเฉย ๆ ไม่ crash ไม่มี error ไม่มี stack trace CPU เป็น 0% แล้วต้องเดาเองว่าค้างตรงไหน 

Thread 1 (โอน A → B)          Thread 2 (โอน B → A)
  lock(mutex A)  สำเร็จ          lock(mutex B)  สำเร็จ
  lock(mutex B)  ← รอ            lock(mutex A)  ← รอ

ต่างคนต่างถือของที่อีกฝ่ายต้องการ ไม่มีใครยอมปล่อย

2 เครื่องมือแทรกตัวอยู่ตรงไหน

ไม่ต้องแก้โค้ดโปรแกรมเป้าหมาย ไม่ต้อง compile ใหม่

โปรแกรมเป้าหมาย        pthread_mutex_lock(&A)
        │
        ▼
libdetect.so  ← โปรเจ็คนี้   1. จดว่า "T1 กำลังจะรอ A"
                            2. เรียกตัวจริง   ← ค้างตรงนี้ตอนเกิด deadlock
                            3. จดว่า "T1 ได้ A แล้ว"
        │
        ▼
libc.so.6                  ตัวจริงที่ทำการล็อก

LD_PRELOAD สั่งให้ dynamic linker โหลด library ของเราไว้หน้าสุด ฟังก์ชันชื่อซ้ำของเราจึงถูกเรียกแทน และเรายังเรียกตัวจริงต่อได้ผ่าน dlsym(RTLD_NEXT, ...)

3 ตรวจเจอได้อย่างไร

สร้าง wait-for graph แล้วหา cycle ด้วย DFS

node คือ thread · edge T1 → T2 แปลว่า "T1 รอ mutex ที่ T2 ถืออยู่" มี cycle = เกิด deadlock แล้ว

thread ของโปรแกรมเป้าหมายค้างกันหมดแล้วก็จริง แต่ detector เป็น thread ของ library เราเอง จึงยังทำงานและรายงานออกมาได้ — ตรวจทุก 500 มิลลิวินาที

4 ลองเอง

เลือกตัวอย่าง หรือวางโค้ด C ของคุณเองลงไปก็ได้

โค้ดถูก compile ด้วย gcc -std=c11 -Wall -Wextra -g -O0 -pthread แล้วรันในโฟลเดอร์ชั่วคราว เสร็จแล้วลบทิ้งอัตโนมัติ

6 ข้อจำกัดที่รู้อยู่

เรื่องรายละเอียด
ดักเฉพาะ pthread_mutex_*rwlock, semaphore, condition variable ยังไม่รองรับ
ต้อง dynamic linkbinary ที่ลิงก์ libpthread แบบ static ใช้ไม่ได้
detection ไม่ใช่ preventionบอกว่าค้างที่ไหน ไม่ได้ทำให้ไม่ค้าง
ชี้บรรทัดต้องมี -gไม่มี debug info ก็ยังบอกได้ว่าใครค้างกับใคร แต่แสดงเป็น pc ดิบ
ไม่รองรับ recursive mutexthread เดิมล็อกตัวเดิมซ้ำจะนับเป็นครั้งเดียว
Linux เท่านั้นLD_PRELOAD เป็นกลไกของ glibc dynamic linker
